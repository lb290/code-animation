## 做了什么
- **定位（量出来的，不是猜的）**：桌面 headless 打开成品后 `performance.memory.usedJSHeapSize = 1276 MB`；`src/geo.js` 的 `B` 把顶点 push 进普通 JS number 数组 —— 205 万三角 = 6770 万个 double（542 MB）+ 610 万索引（49 MB），上传前再整块拷成 Float32Array/Uint32Array（296 MB），峰值 1.2 GB+。安卓 Chrome renderer 堆上限通常 300–500 MB → 直接 OOM。自带浏览器只是「没崩到底」：`world.js` 的 `tag()` 捕获模块异常后继续，内存耗尽的时刻正好落在后面的大模块 → cathedral / station / opera 静默缺失。两个现象一个根因。
- 复现：`--js-flags=--max-old-space-size=350` 加载页面，只有 city 模块打印完成，之后构建卡死（与用户症状一致）。
- **修复**：`B` 增加 `chunked` 模式（Float32Array/Uint32Array 分块 + 每块有效长度 `used[k]`）；`gl.js` 新增 `meshChunked()`（bufferData 定长 + 逐块 bufferSubData，不再整块拷贝）；`world.js` 按 20 万三角预算在模块边界分批上传（本轮 7 批），上传后 `reset()` 复用块、结束时 `release()`；`main.js` 主渲染/阴影 pass 遍历 `world.meshes`。
- 结果：JS 堆 **1276 MB → 29 MB**；构建 2155 → 1551 ms；三角数 2,048,729 **不变**；draw calls 60 → 66；`?diag` 新增「世界批数 / 构建 ms / JS 堆 / 失败列表」，模块失败与 `gl.getError()` 都记进 `ctx.failures`（不再静默缺建筑）。
- 新增 `tools/geo-acc-check.mjs`（跨块逐字节一致 / `used[]` 覆盖率 / `reset()` 复用一致）与 `tools/mem-check.mjs`（受限堆 350 MB 手机模拟 + 桌面，15 条断言），都并入 `checkall`/验收：`checkall` 现 **30 项**。

## 坑与发现
- **块尾空位**：一条顶点 11 个 float 不能跨块，而块容量 262,144 不是 11 的倍数 → 每块尾巴留 0–10 个空位。第一版上传按「整块长度」拷贝，导致后面所有顶点整体错位 3 个 float：屏幕上是城市大块消失 + 黑色剪影 + 彩色竖条。修法是每块记 `used[k]`，只拷有效部分；`geo-acc-check.mjs` 就是为这个坑立的（跨块逐字节比对，含 `reset()` 复用）。
- **chunk 复用与 GC**：每批新建 B 会持续产生 100 MB 级 ArrayBuffer 垃圾，头几十帧被 GC 拖慢（桌面帧时间 18 → 44 ms）。改成 `reset()` 复用块 + 结束 `release()` 后，构建期不再产生垃圾，堆从 1276 MB 降到 29 MB。
- **「带病存活」比崩溃更难查**：`tag()` 的 try/catch 让模块缺失变成静默；现在失败会进 `ctx.failures` 并显示在 `?diag`，下次不会再出现「教堂没了但看不出来为什么」。
- **拖视角检测用错字段**：航线「用户接管」判定最初比较 `cam.lookAt`，但拖视角只改 `yaw/pitch`、不更新 `cam.lookAt` → 拖了也不退出。改用 `cam.forward`（实时视线）后 mobile-check 通过。
- **触屏自动升档**：开机探测预热后帧时间变好，触屏 low 被自动升到 mid —— 这会改变用户看到的画质与发热，且与「触屏默认 low」的约定冲突。改成只降不升，要更高画质用 `?q=mid|high`。
- **lore 的 `zone.view` 与观景点序号错位**（cathedral→43、opera→54、throne→25）：航线按名字/语义配对、用 lore id 打开，不依赖 `zone.view`。
- 显存没有变小：VBO 仍约 271 MB（2.05M tri × 44 B）+ IBO 25 MB。本轮修的是 JS 堆崩溃；若真机仍 context lost，下一步做移动端几何降级（减细分，不删内容）。

## 做了什么
- **先量后改**：新工具 `tools/quality-check.mjs`（CDP 截图 + 纯 Node 解 PNG）量出第 12 轮手机档：

## 坑与发现
- **「不卡」是用分辨率换来的，而且换错了地方**：旧模型把 0.6 当「CSS 像素百分数」，在 dpr 2–3 的手机上
  等于渲染 0.27 MP 再放大 3.3 倍；桌面 dpr=1 却完全正常 —— 所以只有手机会「粗糙」。修渲染管线必须先
  把 `devicePixelRatio` 纳入模型，而不是继续调倍率数字。
- **放大交给浏览器 = 没有锐化**：浏览器的双线性放大是纯糊。真正的观感提升来自「输出分辨率上做锐化」
  （4 tap unsharp），这在 1.4× 上采样时比把场景预算硬拉到 1:1 便宜得多。
- **GPU 计时器比帧时间可靠**：vsync 把 dt 量化成 16.7/33.3，调节器会在这两个值之间跳；GPU ms 才反映
  真正余量。顺带的好处：验收时别的任务抢 GPU（wall frame 31 ms）也不会让调节器误降档。
- **天空顺序**：旧顺序是「先全屏画天空，再让建筑盖上去」。室内机位几乎全是墙，等于把最贵的 shader
  （~380 次噪声采样/像素）白算一遍。改成实体后画 + 深度 1.0 + LEQUAL，室外室内都省，且逐像素一致。
- **背面剔除的诱惑**：2M tri 按说剔背面能省一半，但 winding 不一致（洞里能看见天空）。修 winding 是
  重写全部模块顶点顺序 —— 不值得。已写进技术记录，别再试。
- **触屏「精细」不能带阴影**：阴影是 2M tri 的第二次整场景绘制，与分辨率无关，手机扛不住；
  「精细」在手机上应是更高像素预算 + 更多点光。
- **顺手发现的口径问题**：`scenePx` 是「预算」、`sceneEff` 是「实际渲染像素」（预算被输出封顶）。
  用 `__cielo.stats()` 时别把两者混了（quality-tool 曾报「桌面 scenePx 1.9 MP 而 src 1280×720」，
  其实是预算 1.9 MP、实际被输出封顶到 0.92 MP，属预期）。
